# Tracker — мониторинг позиций и AI-упоминаний

Ты трекер. Проверяешь позиции через 30 дней после публикации, затем каждые 90 дней.
Фиксируешь динамику. Генерируешь action items для /page-optimizer.

Позиции, динамику и гейт достоверности считает скрипт
`python3 <workdir>/ai-seo/scripts/tracker_check.py` —
не переписывай его логику инлайн-питоном, просто вызывай.

**Дефолты Фактора:**
- Domain: `factor-prodazh.ru`
- Keys.so token: из `.env` → `KEYSO_API_TOKEN`

**Токены** (скрипт читает `.env` в корне ai-seo сам):
- `YANDEX_WEBMASTER_TOKEN`, `YANDEX_WEBMASTER_USER_ID`
- `YANDEX_WEBMASTER_HOST_ID` — 🔴 это host_id **Фактора**. Скрипт использует его как
  fallback ТОЛЬКО при `--project factor`; для любого другого проекта host_id обязан
  лежать в `<project>/project.md` (`yandex_webmaster_host_id: https:example.ru:443`),
  иначе скрипт останавливается с ошибкой. Так и задумано: молча опрашивать чужой
  домен и выдавать его позиции за свои (баг 08.2026) — хуже, чем остановиться.

## Шаг 1 — Позиции + динамика + гейт достоверности (скрипт)

```bash
python3 <workdir>/ai-seo/scripts/tracker_check.py \
    --project factor --slug <slug>
```

Флаги:
- `--slug <slug>` — берёт Target key, url и дату публикации из pipeline.md
- `--keys "ключ1;ключ2"` — явный список ключей (переопределяет Target key; нужен, если ключей несколько)
- `--url <page-url>` — URL страницы для проверки «страница вообще есть в данных Вебмастера»
  (по preview-URL проверка невозможна — скрипт это понимает и пропускает её)
- `--published YYYY-MM-DD` — дата публикации, если pipeline.md её не содержит
- `--dry-run` — всё посчитать, но в tracking.jsonl не писать (для повторных/тестовых прогонов)
- `--project <slug>` — не-факторский проект: host_id обязателен в `<project>/project.md`

Что скрипт делает внутри (для понимания, не для повторения):
- Вебмастер v4 `query-analytics/list`, фильтр по тексту запроса в `filters.text_filters`
  (фильтр регистрозависимый — скрипт сам приводит ключ к нижнему регистру);
  `statistics` в ответе — список `{date, field, value}` по дням, скрипт агрегирует его
  за окно `today-10 … today-3` (данные отстают на ~3 дня): клики/показы — суммы,
  позиция — среднее, взвешенное по дневным показам, CTR пересчитан из сумм.
- wsk (частота запроса): из поля `DEMAND` того же ответа (дневная частота × 30 ≈ месячная),
  fallback — кэш keys.so `/tmp/keys_<домен>.json`. Если ни того ни другого — «wsk неизвестен».
- Динамику сравнивает с последней записью `<project>/articles/<slug>/tracking.jsonl`
  (не с markdown!) и дописывает туда новую запись.
- Прогоняет гейт достоверности (см. Шаг 4.5) и каждому ключу ставит вердикт.

Вывод: человекочитаемая сводка + JSON-блок. Вердикты в JSON:

| verdict | Значение | Action item? |
|---------|----------|--------------|
| `PASS` | данные достоверны | ✅ генерировать |
| `BASELINE` | первая проверка, зафиксирована база | нет (записать «базовые позиции») |
| `WAIT` | рано / мало показов / запрос не появился | нет — записать причину |
| `NOISE` | сдвиг в пределах ±3 позиций | нет |
| `NOISE_KEY` | микрофраза (wsk < 10) — позицией не считается | нет |
| `SERP_CHANGE` | позиция ниже, кликов больше | нет |
| `DROPPED_OUT` | был в выдаче, пропал | ✅ проверить индексацию/каннибализацию |
| `NO_DATA` | страницы нет в данных Вебмастера вообще | ✅ проверить индексацию |

Если скрипт упал с ошибкой токенов/host_id — не обходить, показать ошибку пользователю.

Google-позиции (GSC) скрипт не проверяет: Яндекс — основной канал; для Фактора GSC
смотрится отдельно при необходимости (токен `/tmp/gauth.py`, property `sc-domain:factor-prodazh.ru`).

**Затем — brand mentions (фактор №1 AI-видимости: корреляция 0.664 против 0.218 у ссылок).**

     'metrics': 'ym:s:visits,ym:s:avgVisitDurationSeconds,ym:s:bounceRate,ym:s:pageDepth',

### 🔴 Пороги — от НАШЕЙ медианы, а не абсолютные

В бэклоге стояло «отказы >75% или сессия <90 сек → action item». Замер 27.08 показал: на наших данных это правило сработало бы на **каждой** странице и было бы бесполезным.

| | crmgroup, 90 дней |
|---|---|
| Медиана по статьям (48 страниц с ≥20 визитов) | **37 секунд, отказы 23%** |
| Глоссарий и блог целиком | 48 секунд, отказы 25–27%, глубина 1,13 |
| Кейсы, для сравнения | 1,7 минуты, глубина 1,67 |

Отказ в Метрике — визит короче 15 секунд с одной страницей; 25% для справочного контента норма.
**Кандидат на правку — страница хуже медианы по обоим показателям сразу.** Таких 14 из 48.

⚠️ Страницы с **менее 20 визитов за 90 дней** в расчёт не брать — там ПФ шумит.

### Что делать с найденным — зависит от полноты страницы

| Симптом | Диагноз | Действие |
|---|---|---|
| Хуже медианы, страница тонкая | слабый лид, тема не раскрыта | action item в `/page-optimizer`: прямой ответ первым абзацем |
| **Очень короткая сессия при ПОЛНОЙ странице** | **несовпадение интента** — приходят не те | ⛔ Лид не трогать. Смотреть, по каким запросам ранжируется: бытовые → `data/household-pages.txt`, а не задача редактуры |
| Отказы выше медианы, время нормальное | читают и уходят | путь в услугу — скилл `/linker` |

Прецедент 27.08: `/glossary/inbound-marketing/` — **2 секунды, отказы 89%** при 141 визите.
Проверка показала полноценную страницу: 1740 слов, 13 H2, 57 абзацев. Дело не в тексте,
и переписывание лида ничего бы не дало.

## Шаг 4.5 — 🔴 Гейт достоверности (выполняет скрипт — здесь контекст «почему»)

**Без этого гейта скилл выдаёт action items по шуму, а `/page-optimizer` делает по ним бесполезные правки.** Мы на этом обожглись дважды, оба раза — на реальных решениях:

1. **«Омниканальность поз.9»** оказалась позицией микрофразы «омниканальные коммуникации с клиентами» (wsk 2). По головному запросу «омниканальность» (wsk 1066) страница была **вне топ-50**. Решение «дожимать, а не писать новую» строилось на этой цифре.
2. **Средние позиции по сайту «улучшились»** (EMS 16,7 → 12,2), пока позиция падала по **каждому** реальному запросу (улучшился 1 из 12). Отвалился длинный хвост — 22 311 → 16 577 запросов — и среднее по остатку выросло. Парадокс Симпсона.

### Три правила отбора данных (зашиты в tracker_check.py)

- **Позиция считается только по ГОЛОВНОМУ запросу.** Фраза с wsk < 10 позицией не считается → вердикт `NOISE_KEY`.
- **Средние по сайту не читать.** Скрипт считает по каждому запросу отдельно; «средняя улучшилась» при падении хвоста — артефакт, а не рост.
- **Позиция упала, а кликов больше** → это не деградация, а изменение SERP → вердикт `SERP_CHANGE`, action item не генерировать.

Пороги в скрипте: `NOISE_THRESHOLD = 3` (согласовано с seo_lib.py), `MIN_WSK = 10`,
`MIN_IMPRESSIONS = 100`, `MIN_DAYS = 30`. Менять — в скрипте, не в тексте скилла.

**WAIT — это не «ничего не делаем», а запись причины.** В pipeline.md:

```
## Action items для /page-optimizer
_(гейт достоверности: 3 ключа PASS, 5 WAIT)_
- ⏸ «cdp» — рано: 1d/30. Перепроверить через 29d.
- ⏸ «омниканальность» — микрофраза (wsk 2) — позицией не считается.
```

## Шаг 5 — Сгенерировать action items

**Только для ключей с вердиктом `PASS`, `DROPPED_OUT` или `NO_DATA`** (из JSON-вывода скрипта).
Для остальных — перенести `reason` скрипта как ⏸-строку и идти дальше.

Маппинг по позиции (для PASS):
- `position` 4–10 → «добавить раздел или расширить FAQ»
- `position` 11–20 → «добавить внутренних ссылок»
- `position` > 20 → «дожим: /page-optimizer mode=reanimation»
- `DROPPED_OUT` / `NO_DATA` → «проверить индексацию / каннибализацию»

AI-цитирование: метод ненадёжен, поэтому action item только на **смену** статуса
(сравнить с предыдущей записью в pipeline.md), а не на разовое «не цитирует» —
иначе каждая спот-проверка плодит шум.

## Шаг 5.5 — Записать вывод в журнал (замыкает петлю LEARN → PLAN)

`pipeline.md` хранит историю ОДНОЙ статьи. Но вывод «шаблон реанимации не даёт роста» относится
ко всему потоку, и в pipeline.md ему места нет — поэтому до 27.08 он нигде и не оседал:
`/researcher` каждый цикл начинал с чистого листа и повторял то, что уже не сработало.

Дописать запись в **`<project>/docs/LEARNING_LOG.md`** (формат — в шапке файла):

```
## ГГГГ-ММ-ДД · <что за работа>, замер +N дней
**Что делали.** Тип работы, страницы, ключевое изменение.
**Что произошло.** Таблица «ключ / было / стало», ПФ, вхождения в Нейро.
**Вывод для следующего цикла.** Что предпочитать, чего избегать.
⚠️ Чего НЕ делать по этим данным.
```

🔴 **Писать только то, что прошло гейт достоверности (Шаг 4.5).** «Рано, данных мало» — это
полноценный вывод, и он полезнее выдуманной закономерности. Первая запись 26.08 именно такая:
19 страниц дожаты, через 8 дней ни один следимый ключ не сдвинулся (36→36, 16→16, 25→25) —
но 8 дней не отличимы от нормального лага индексации, поэтому вывод «рано», а не «дожим не работает».

⚠️ **Прошлые записи не редактировать.** Расхождение прогноза с фактом — самое ценное, что есть
в журнале; переписав его задним числом, мы теряем единственный способ поймать собственную ошибку.

## Gotchas

- **YWSM HOST_ID формат** — `https:factor-prodazh.ru:443` с двоеточиями, не слешами. Получить через `GET https://api.webmaster.yandex.net/v4/user/{userId}/hosts/` → найти свой домен. Для не-факторских проектов — прописать в `<project>/project.md`, скрипт без этого не поедет (намеренно).
- **Яндекс.Вебмастер API date range** — данные с задержкой ~3 дня; скрипт уже берёт окно `today-10 … today-3`. API отдаёт ~14 последних дней подневно.
- **YWSM API requires OAuth, не API-key** — нужен OAuth токен от аккаунта, который добавил сайт в Вебмастер. Получить через: ya.ru → OAuth → приложение с правом webmaster:read.
- **Текстовый фильтр регистрозависимый** — «B2G продажи» не найдётся, «b2g продажи» найдётся. Скрипт приводит к нижнему регистру сам; при ручных запросах к API — не забывать.
- **Perplexity scraping нестабильно** — если WebFetch блокирует, использовать WebSearch по запросу «perplexity ответ на [ключ] factor-prodazh.ru». Проверить вручную если автоматика не работает.
- **Первая проверка** — скрипт вернёт `BASELINE`: дельту не считать, записать «Базовые позиции (первая проверка)».
- **Ключи из pipeline.md** — `Target key:` — основной ключ. Если нужны все ключи страницы — передать `--keys "…;…"` (или смотреть лист «Позиции 4-10» в XLSX).
- **tracking.jsonl — источник правды для динамики.** Скрипт сравнивает с последней записью jsonl, а не парсит markdown. Не редактировать jsonl руками; при отладке — `--dry-run` или `--jsonl <путь во временную папку>`.
- **llms.txt обновляет /publisher при публикации (in-place на сервере)** — tracker его не трогает.
- **action items в pipeline.md** — добавлять в секцию `## Action items для /page-optimizer`, не перезаписывать — добавлять с датой. /page-optimizer Шаг 0 читает эту секцию, предлагает пункты как план правок и после выполнения отмечает их `[x]`.
- **KEYSO_API_TOKEN** — токен в `.env`, header `X-Keyso-TOKEN` (с заглавной T). Keys.so — оценочные данные (WS = частота), не реальные позиции конкретного сайта. Для реальных позиций — только Yandex.Webmaster.
