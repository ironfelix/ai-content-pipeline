**Перед ресёрчем проверить: нет ли уже статьи под этот ключ/интент.** Дубль = каннибализация позиций, два URL конкурируют в выдаче и оба проседают. Прецедент: батч 2026-06-11, «выявление потребностей» — дубль опубликованной статьи поймали уже после написания (пришлось ставить 301).

### 🔴 Сначала определить ОБЛАСТЬ поиска — иначе чек проверит половину

Чек ищет ровно там, куда его послали. Если у проекта больше одного сайта или больше одной папки со статьями, а ты проверил одну — чек вернёт «чисто» и будет неправ.

**Перед поиском выписать:**
- **все домены проекта** — не только тот, для которого пишем;
- **все корни со статьями** — `articles_dir` из project.md может быть не единственным.

Для **crmgroup / emailsoldiers** это буквально так (проверять оба, всегда):

| | Домены | Корни со статьями |
|---|---|---|
| | `crmgroup.ru` + `emailsoldiers.ru` | `<workdir>/01-crmgroup/articles/` **и** `ai-seo/crmgroup/articles/`, `ai-seo/emailsoldiers/articles/` |

> Прецедент 08.2026: чек гонялся из `01-crmgroup` и не видел `ai-seo/crmgroup/articles/lidogeneraciya-dlya-biznesa/`. Дважды разошлись темы — «лидогенерация» (план crmgroup против живой статьи EMS) и ROI (crmgroup против `/glossary/roi` EMS). Шаг был реализован и при этом проверял половину.

**1. Поиск по опубликованным (WP REST) — по КАЖДОМУ домену проекта:**

```python
import requests
# SITES: [(WP_URL, WP_AUTH, rest_base), ...] — ВСЕ домены проекта из project.md, не только целевой.
# rest_base отличается: crmgroup — blog/glossary, EMS — posts/glossary, база знаний — academy.
for wp_url, auth, base in SITES:
    for query in [target_key, *synonyms]:  # синонимы: «выявление потребностей» ≈ «вопросы клиенту»
        resp = requests.get(
            f"{wp_url}/?rest_route=/wp/v2/{base}",
            params={"search": query, "per_page": 20, "_fields": "id,slug,title,link,status"},
            auth=auth,
        )
        for p in resp.json():
            print(wp_url, base, p["id"], p["slug"], p["title"]["rendered"])
```

**2. Поиск по локальным черновикам (ещё не опубликованные, но уже в работе) — по ВСЕМ корням:**

```bash
# перечислить все корни проекта, не только текущий
grep -ril "<главное слово ключа>" \
  <workdir>/01-crmgroup/articles/*/pipeline.md \
  ai-seo/*/articles/*/pipeline.md 2>/dev/null
```

**3. llms.txt как быстрый индекс опубликованного** — тоже по каждому домену: `curl -s {WP_URL}/llms.txt | grep -i "<слово>"`

**Решение по результату:**

| Ситуация | Действие |
|----------|----------|
| Точный ключ уже закрыт опубликованной статьёй | СТОП. Предложить пользователю: rewrite существующего поста (обновить контент в тот же URL) вместо новой статьи |
| **Наша страница уже в топ-50 по головному запросу** | СТОП. Дожимаем её (`/page-optimizer` режим `reanimation`), а не поднимаем второй URL — даже если это ломает распределение тем по сайтам |
| **Тема закрыта на ПАРНОМ домене** | СТОП. Правило: одна тема живёт на одном сайте, второй ставит ссылку. Показать пользователю обе страницы и предложить, кому тема принадлежит по ролям сайтов |
| Смежная статья с пересечением интента >50% | Сменить угол: новый ключ должен закрывать ДРУГОЙ интент. Зафиксировать различие интентов в Research Report |
| Черновик в работе на ту же тему | СТОП, показать пользователю оба слага |
| Пересечения нет | Записать в pipeline.md: `cannibalization_check: ✅ чисто (проверено N запросов, домены: …, корни: …)` и продолжить |

⚠️ **Позиция считается только по ГОЛОВНОМУ запросу.** Похожая фраза с wsk < 10 позицией не считается: «омниканальность поз.9» оказалась микрофразой «омниканальные коммуникации с клиентами» (wsk 2), тогда как по головному «омниканальность» (wsk 1066) страница была вне топ-50. На этой ошибке однажды построили решение.

Результат чека всегда фиксировать в Research Report (раздел 0) — какие запросы проверены, что найдено.

## Шаг 1а — Pre-research гипотезы *(новый)*

**Выполнять ДО чтения конкурентов.** Это предотвращает confirmation bias — когда читаешь то, что ожидаешь найти.

Сформулировать 3 гипотезы:

```
Гипотеза 1 (угол): «Предполагаю, что уникальный угол будет X, потому что...»
Гипотеза 2 (пробел): «Конкуренты скорее всего не покрывают Y, потому что...»
Гипотеза 3 (спор): «Спорный тезис, который можно защитить: Z»
```

После завершения ресёрча (Шаг 4) — вернуться и проверить каждую:
- ✅ Подтвердилась — зафиксировать
- ❌ Опровергнута — объяснить что оказалось иначе (это ценнее подтверждения)
- ❓ Нет данных — отметить как «unknowns»

**Правило:** если все три гипотезы подтвердились без сюрпризов → ресёрч недостаточно глубок. Копать дальше.

## Шаг 1б — Query fan-out кластер

**После формирования основных запросов** — развернуть семантический кластер.

Google AI генерирует веер смежных запросов вокруг темы (Query fan-out) и собирает ответы из нескольких источников. Контент, покрывающий кластер целиком, попадает в AI-ответ с кратно большей вероятностью.

Для основного ключа сгенерируй **5–8 смежных вопросов**, на которые Google AI может искать ответ при вводе основного запроса:
- «как [основной ключ] пошагово»
- «[основной ключ] ошибки / типичные проблемы»
- «чем отличается [основной ключ] от [смежного понятия]»
- «когда [основной ключ] не работает»
- «[основной ключ] примеры / кейсы»

Зафиксируй список в research-файле (раздел 1б). Используй при составлении структуры H2 — каждый пункт структуры должен закрывать хотя бы один fan-out вопрос.

**Анти-спам правило:** один кластер = одна глубокая статья. Создавать отдельные страницы под каждый fan-out запрос — нарушение спам-политики Google. Если кластер слишком широкий → выбрать один центральный угол, остальное — как H2 внутри одной статьи.

**Перед разведкой по вебу — собрать то, чего НЕТ в вебе.** Это главный источник неповторимого угла. Веб-топ есть у всех конкурентов; уникальность — вне его.

Собрать из `company_context` (project.md) + спросить пользователя, если не передано:

2. **Экспертный инсайт** — что практик знает, чего нет в статьях (нюанс, исключение, «так делают, а надо иначе»).

## Шаг 2 — Многоагентный fan-out разведки *(переработано — глубина вместо топ-10)*

**Не линейное чтение топ-10 одним проходом.** Запустить **4 субагента-разведчика параллельно** (Agent tool, в ОДНОМ сообщении — несколько вызовов), каждый со СВОИМ углом и своим набором источников. Это даёт 30–40 источников + разные перспективы (контрарианец находит то, что аналитик пропустит) = настоящий угол, а не рерайт.

**4 разведчика (каждый = отдельный субагент, agentType Explore или general-purpose):**

| Агент | Задача | Где ищет |
|-------|--------|----------|
| **АНАЛИТИК** | как тему раскрывают лидеры выдачи: структура, факты, цифры, что считается стандартом | топ-10 Яндекс/Google статьи |
| **КОНТРАРИАНЕЦ** | где мейнстрим неправ/упрощает; альтернативные мнения; «почему советы из топа не работают» | дискуссии, критика, нестандартные и EN-источники |
| **ПРАКТИК** | как это РЕАЛЬНО делается: пошаговые гайды, грабли внедрения, скрытые издержки, реальные цены/тарифы (проверить, не из статей) | кейсы, инструкции, документация и прайсы сервисов |
| **ЖИВАЯ БОЛЬ** | реальные вопросы и возражения аудитории — НЕ вылизанные статьи | форумы, комменты vc.ru/Habr, тематические TG/сообщества, отзывы, «Люди также спрашивают» |

Каждому агенту дать: тему, целевой ключ, fan-out-кластер (Шаг 1б), и схему отчёта:
```
Найденные источники (URL + тип): ...   (минимум 7-10 на агента)
Ключевые факты/цифры (с источником): ...
Что уникального нашёл под своим углом: ...
Чего НЕТ ни у кого по теме: ...
```

**АНАЛИТИКУ — дополнительное ОБЯЗАТЕЛЬНОЕ поле отчёта** (по нему потом считается Шаг 4а, повторного чтения топ-5 не будет):
```
Топ-5 по целевому ключу — ПО КАЖДОМУ из 5:
  URL: ...
  Структура H2/H3: полный список заголовков
  Форматные элементы: таблица / формула / калькулятор / пример с цифрами /
    скрипты-готовые фразы / диалог / шаблон-чеклист / схема / видео — что есть
```
АНАЛИТИК читает топ-5 через WebFetch полностью (не сниппеты). Если какой-то URL не отдался — писать «не отдался», не реконструировать структуру.

**Каждый агент возвращает свои находки** (вывод, не сырой дамп). Собрать ответы 4 агентов = широкая база источников + 4 угла. Дедуп URL. Зафиксировать в разделе 2 (с пометкой какой агент что нашёл).

Если тема узкая и 4 агента избыточны — минимум 2 (АНАЛИТИК + КОНТРАРИАНЕЦ или ПРАКТИК). Но «живую боль» (форумы) не пропускать — там настоящие вопросы аудитории.

## Шаг 2б — Contrarian pass *(финальная сверка)*

**После сбора находок 4 агентов** — перечитать лучшую статью конкурента с одним вопросом:

> «Что в этой статье правда, даже если нам неудобно это признавать?
> Что конкурент делает лучше, чем мы можем сделать?
> Какой его тезис реально сильнее нашего?»

Зафиксировать 1–3 пункта. Это не слабость — это честность. Возможные выводы:
- **Конкурент прав** → наш угол надо переосмыслить
- **Конкурент прав, но у нас есть лучший пример** → использовать его данные + наш кейс
- **Конкурент прав в теории, мы знаем практику** → это и есть уникальный угол

Если нет ни одного пункта → contrarian pass не завершён. Любая статья имеет что-то ценное.

   - **T1** — оригинальный отчёт проверен: название + год + реально читал
   - **T2** — крупное СМИ со ссылкой на конкретный отчёт
   - **T3** — факт известен, источник не найден → в статье «по оценкам рынка» без названия
   - **X** — не использовать (источник не читал, но называет)

3. Дополнительно — проверить базу `factor/research/knowledge-base-sales-industry.md` на наличие верифицированных данных.

**Правило:** нет названия отчёта + года → понизить до T3. Данные старше 3 лет → добавить пометку.

**Contested claims deepening (итеративное углубление):** для каждого факта, важного для аргументации, оценить уверенность. Если факт спорный / источники расходятся / confidence низкая — **запустить доп. целевой проход** (WebSearch за первоисточником, при необходимости — отдельный субагент на этот спорный пункт). До 2 раундов углубления на спорный факт. Если после этого источник не найден → T3 без названия или убрать. T3 с названием источника, который не читал, = X.

## Шаг 3б — Раздельная верификация цифр *(новый — fact-check)*

**После сбора фактов — отдельный проверочный проход по числам** (не та же логика, что собирала, — свежий взгляд ловит ошибки).

**Опорные 3–5 цифр статьи → отдельный субагент-верификатор ПО УМОЛЧАНИЮ** (не опция). Выбрать из фактов 3–5 чисел, на которых держится аргументация (цены, %, бенчмарки, размеры рынка), и запустить субагент (Agent tool) с заданием: «Вот список численных утверждений с заявленными источниками. Для каждого — независимым поиском проверь: подтверждено (≥2 источника или первоисточник) / расходится (какой диапазон) / не найдено. Не доверяй формулировкам списка — ищи сам.» Субагенту НЕ передавать ход рассуждений сессии — только сами утверждения.

Остальные численные утверждения (обычно ещё 5–10):
1. Перепроверить независимым запросом в сессии — сходится ли с ≥2 источниками или первоисточником.
2. Пометить расхождения: если источники дают разные цифры — указать диапазон в отчёте.
3. Цены/тарифы/быстро меняющиеся данные → пометка «на [месяц год], проверить перед публикацией».

Вердикт «не найдено» от верификатора → цифра понижается до T3 без числа или убирается. Зафиксировать результат в разделе 3 (колонка «верифицировано ✓/диапазон/⚠️», опорные цифры — с пометкой «субагент»).

## Шаг 4а — Полнота интента (intent-completeness vs топ-5) *(измеримо)*

Gap-матрица Шага 4 качественная («на глаз»). Этот шаг переводит её в **число** и в чек-лист покрытия, который контролирует H2-план. Отвечает на вопрос «чем наша будущая статья беднее топ-5» ещё до написания.

**Три слоя (слой 3 — если есть `KEYSO_API_TOKEN`, иначе пропустить, модуль работает и на 1–2):**

1. **Топ-5 конкурентов.** Сторона Google уже есть из затравочных WebSearch (Шаг 1) и находок АНАЛИТИКА. Яндексовый топ — из keys.so (слой 3, поля serp/позиции), НЕ из головы: выдача Я≠G, страница бывает полна для одного и дырява для другого. Исключить: свой домен, агрегаторы-маркетплейсы, видео.
2. **Структуры топ-5 — считать по данным АНАЛИТИКА (Шаг 2), НЕ фетчить топ-5 повторно.** В его отчёте обязательное поле: H2/H3 + форматные элементы по каждому из топ-5. Точечный WebFetch — только для URL, которого у АНАЛИТИКА нет (не покрыл / страница не отдалась / яндексовый топ дал другой URL).
   - **Консенсус-скелет** = подтемы у ≥3 из 5. **Консенсус-форматы** = форматы у ≥3 из 5.
3. **keys.so — количественный слой (наша сторона).** У `report/simple/organic/keywords` в каждой записи есть поле `url` → вытянуть ключи домена и отфильтровать по `url == /blog/<slug>/` (для рерайта существующей) или по смежным нашим URL. Даёт объективно, не «на глаз»:
   - облако запросов, которые уже ловим + позиции; **pos 4–15 = near-miss**, точные кандидаты в дозаполнение;
   - `isquest==1` → реальные вопросы-запросы прямо в FAQ;
   - `wizards`/`wizardscount`/`serpf` → какие ключи триггерят SERP-колдунщики/AI-блоки = zero-click риск (передать в замер ИИ-выдачи).
   Конкурентов через keys.so НЕ тянуть по умолчанию — нет эндпоинта «URL→ключи», фильтр требует полной выгрузки домена (кредиты). Структуру конкурентов берём из WebFetch (слой 2).

**Diff и метрики:**
- **ДЫРЫ** — консенсус-подтемы/форматы, которых у нас нет. Приоритет: 5/5 → 4/5 → 3/5.
- **УНИКАЛЬНЫЙ УГОЛ** — что есть только у нас (из Шага 4). Пометить «сохранить» — дозаполнение дыр его не затирает.
- **Две метрики РАЗДЕЛЬНО** (общий % маскирует форматную дыру — реальный кейс: страница богата подтемами, но проигрывает в Google из-за отсутствия скриптов/диалогов):
  - completeness подтем = покрытые консенсус-подтемы / всего;
  - completeness форматов = покрытые консенсус-форматы / всего.
- **Порог:** <70% по любой из двух → H2-план обязан закрыть дыры. Уникальный угол обязателен (hard-gate) независимо от %.

**Skyscraper — правильный:** закрыть консенсус-дыры + дать своё, а НЕ «сделать длиннее». Прикладной слой (скрипты, пример, таблица) добавлять поверх глубины, не вместо. Против правил о воде — объём есть следствие закрытых дыр, не цель.

Зафиксировать блок в research-файле (раздел 4а) и позже в pipeline.md:
```
intent_gap:
  движок: Google | Яндекс | оба
  топ-5: [домены]
  completeness: подтемы XX% / форматы YY%
  near-miss (keys.so, pos 4-15): [ключи или «keys.so не запускался»]
  дыры (приоритет): [5/5] ... · [4/5] ... · [3/5] ...
  уникальный угол (сохранить): ...
```

Каждая дыра высокого приоритета (5/5, 4/5) должна стать пунктом H2-плана (Шаг 6) — иначе writer её пропустит.

### Вопросы аудитории → FAQ и H2 (бэклог #9)

Рядом с кластером собрать **вопросные формулировки** — то, как люди спрашивают на самом деле. Это прямое сырьё для FAQ и для H2, которые должны быть самостоятельными запросами.

```python
import json, collections
rows = json.load(open('/tmp/keys_crmgroup_ru.json'))
seen, qs = set(), []
for r in rows:
    if r.get('isquest') != 1:      # keys.so сам размечает вопросные запросы
        continue
    w = (r.get('word') or '').strip()
    if w in seen:                  # 🔴 keys.so отдаёт ДУБЛИ — без дедупа топ забьётся одной фразой
        continue
    seen.add(w)
    qs.append((r.get('superwsk') or 0, r.get('pos') or 99, w))
qs.sort(reverse=True)
```

Замер 27.08 по crmgroup: из 2000 ключей кэша **474 помечены вопросами**, средняя длина 4,6 слова. Без дедупа первые четыре строки топа — одна и та же фраза «что такое кликбейт».

**Чем дополнить, потому что keys.so видит не всё:**
- `python3 <workdir>/01-crmgroup/scripts/wordstat_cloud.py "<головной запрос>" 50` — хвосты реже 30/мес, которые keys.so не индексирует;
- GSC-запросы от 7 слов — там живут развёрнутые формулировки, близкие к тому, как спрашивают у ассистентов.

Сохранить рядом с research-файлом как `prompts.md`: вопрос, спрос, текущая позиция. Использовать в FAQ (минимум 4 вопроса — берутся отсюда, а не выдумываются) и при формулировке H2.

**Эти вопросы включить в раздел «FAQ-кандидаты» research-файла** (см. шаблон, раздел 4а) — writer читает research-файл, `prompts.md` — вспомогательный архив, до writer он не доходит.

⚠️ **Не выдавать это за «промпты к LLM».** Мы наблюдаем поисковые вопросы, а не запросы к ассистентам — данных по вторым у нас нет. Разница в длине заметна: 4,6 слова против 7 в открытых оценках по LLM. Формулировки полезны как есть, но подписывать их надо честно.

⚠️ **Кластер — не список ключей для вставки.** Дописывают ОТВЕТ на запрос: абзац, определение, пример расчёта. Вставка самих ключей ловится М28 как переспам, и справедливо.

**Gotchas модуля:** страница из топ-5 не отдалась ни АНАЛИТИКУ, ни точечному WebFetch → отметить, считать по доступным (не выдумывать структуру конкурента). keys.so `domain=<URL>` НЕ фильтрует по странице (вернёт весь домен) — фильтровать по полю `url` в записях уже после выгрузки. Не путать «мало текста» с «дырой» — дыра это отсутствующая *подтема/формат*, а не длина. Уникальный угол приоритетнее полноты: 100% покрытия без своего угла = статья-клон.

## Шаг 4б — CRITIC-pass *(субагент — обязательный)*

**Обязательный adversarial шаг, и делает его НЕ та сессия, что породила угол.** Контекст, который придумал угол, будет его защищать — это слабая адверсарность. Поэтому критик — отдельный субагент со свежим контекстом.

Порядок:
1. Собрать черновик Research Report (разделы 0–5 + формулировка угла и H2-плана) — тот же текст, что пойдёт в файл на Шаге 6.
2. Запустить субагент (Agent tool). **Вход — ТОЛЬКО текст отчёта.** Не передавать ход рассуждений сессии, находки разведчиков сырьём, свои оправдания угла. Промпт: «Ты адверсарный критик. Атакуй угол и факты этого research-отчёта: найди, чем статья по нему будет водой, что легче всего опровергнуть, где угол — рефрейм чужого. Ответь на каждый из вопросов ниже конкретно, без дипломатии.» + 5 универсальных вопросов + domain-специфичные (Шаг 0.7 / references/domains.md).
3. Все ответы критика зафиксировать в research-файле (раздел 4б, все 5 слотов). Согласен/не согласен — тоже написать: несогласие с критиком аргументируется, а не игнорируется.

**Универсальные CRITIC-вопросы (передать субагенту):**
1. Главный тезис — это реально уникальная позиция или просто другими словами то, что пишут конкуренты?
2. Какой раздел статьи читатель назовёт «водой» или «слишком теоретическим»?
3. Где в аргументации самое слабое звено — что легче всего опровергнуть?
4. Есть ли T1/T2 источник, который прямо противоречит углу? Как с ним работать?
5. Если бы конкурент писал антитезис к этой статье — что бы он написал?

Если по вопросам 1 и 4 у критика нашлись дыры без честного ответа → ресёрч не завершён, вернуться в Шаги 2–4, а не сдавать отчёт.

## Gotchas

- **Не читать геолокацию из домена** — `.yaroslavl.ru`, `.msk.ru` и т.п. не говорят о регионе работы. Брать только из brief.md.
- **Не придумывать кейс** — если подходящего нет в company-context.md / cases_url, написать явно. Нельзя брать похожий и адаптировать.
- **T1 — только если реально читал** — не повышать уровень источника потому что он звучит авторитетно. Нет прочтения → T3 или X.
- **Contested claims → deepening обязателен** — если факт T3, но центральный для аргумента — один дополнительный поисковый проход. Иначе это слабое место для критики статьи.
- **WebFetch = полная страница, не сниппет** — это правило для АНАЛИТИКА (читает топ-5 целиком) и для любого точечного добора; описанию из поисковой выдачи не доверять. Повторно фетчить топ-5 в Шаге 4а не нужно — данные уже в отчёте АНАЛИТИКА.
- **Если уникального угла нет — сказать явно** — не придумывать «уникальность». Честный ответ лучше клонированной статьи.
- **Тип статьи по умолчанию — гайд** — другие типы только если явно задан в брифе.
- **domain != company: gotchas своего домена** — в `references/domains.md` (health: T3 для клинических утверждений = X; macro: прогноз без трек-рекорда = T3; science: статус препринта). Прочитать вместе с гейтом.
- **Contrarian pass нельзя пропустить** — если пройден формально («конкурент ничего хорошего не написал») — это confirmation bias, не завершённый шаг.
- **Если все 3 pre-research гипотезы подтвердились** — докопаться глубже. Полное совпадение = ресёрч слишком поверхностный или тема слишком очевидна.
- **Fan-out агенты — в ОДНОМ сообщении** (несколько Agent-вызовов параллельно), иначе теряется смысл параллельности. Каждый возвращает вывод, не сырой дамп страниц.
- **Угол только на вебе = красный флаг** — если в разделе 1.5 первички нет, честно пометить «риск рерайта» и предложить пользователю дать данные/экспертку. Веб-gap часто пуст потому что нет данных, а не потому что тема не раскрыта.

## Принципы

- **Глубина через fan-out, не через топ-10 одним проходом** — 4 субагента с разными углами дают 30+ источников + перспективы. Один линейный проход = рерайт.
- **Первичка > веб** — уникальный угол рождается из того, чего НЕТ в вебе (данные компании, экспертка, форумы). Веб-топ есть у всех конкурентов.
- **Живая боль обязательна** — форумы/комменты/отзывы дают реальные вопросы аудитории, которых нет в вылизанных статьях.
- Читать страницы полностью через WebFetch, не только сниппеты из поиска
- Не выдумывать факты — только то, что реально прочитано
- Если источник не верифицирован — T3, не T1; цифры — отдельный проверочный проход (Шаг 3б)
- Кейсы клиента — только из проверенных источников
- Уникальный угол важнее объёма — лучше честно сказать «угла нет», чем писать статью-клон
- Adversarial review (CRITIC-pass) — не опция, а обязательный шаг; критикует субагент по готовому отчёту, не контекст, породивший угол
