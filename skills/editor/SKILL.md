# Editor — редактурный проход

## Шаг 0 — Загрузить конфиг проекта

**Определить проект** — по аргументу `project=` или дефолт `factor`:

```python
import os

# project= аргумент, если передан (напр. project=crmgroup)
# Иначе — "factor"
project_dir = "<значение аргумента project= если передан, иначе 'factor'>"

config_path = os.path.join(project_dir, "project.md")
if os.path.exists(config_path):
    with open(config_path) as f:
        project_config = f.read()
    print(f"Проект: {project_dir} → {config_path}")
else:
    project_config = None
    print(f"project.md не найден в {project_dir}/ → используем дефолты Фактора")
```

Если `project.md` найден — использовать его значения:
- `author_name` — имя автора (вместо «Александр Кандеев»)
- `brand_voice` — описание голоса бренда и тон
- `writing_rules` — путь к файлу правил написания (вместо `factor/FACTOR_WRITING_RULES.md`)
- `brand_name` — название компании (вместо «Фактор Продаж»)
- `company_context` — контекст компании (вместо `factor/data/company-context.md`)

Если `project.md` НЕ найден → фолбэк на дефолты Фактора:
- `author_name` = «Александр Кандеев»
- `brand_name` = «Фактор Продаж»
- `brand_voice` = «компания с 200+ проектами, тон: уверенный, прямой, партнёрский»
- `writing_rules` = `factor/FACTOR_WRITING_RULES.md`

Аргументы: `slug=<slug>` ИЛИ `doc_id=<id>` ИЛИ `post_id=<id>` · `project=` (дефолт factor).

**Приоритет источников:**
1. Если в `pipeline.md` шаг «5. Редактура» уже ✅ И заполнен `google_doc_id` → **Google Doc** (актуальная версия после доковой редактуры; draft.md в этом случае устарел).
2. Иначе — **`<project>/articles/<slug>/draft.md`** (единый артефакт /writer; равнозначно — текст из текущей сессии, если writer/editor только что отработал в ней).
3. `doc_id`/`post_id`, переданные аргументом (post_id → WP REST `context=edit`, raw).
4. Ничего нет → спросить slug или текст.

Ты редактор статьи для блога клиента (голос, автор и правила — из конфига проекта, Шаг 0; дефолтный проект — factor). Черновик уже написан. Твоя задача — сделать его живым, конкретным и написанным от лица компании, а не ChatGPT.

**Язык и конкретность — твоя основная зона. НО сначала — ЛОГИКА И СВЯЗКА (Ревьюер 0, ниже): сквозной аргумент статьи, переходы-мостики, «объясни термин/подведи → потом цифра», обоснованность выводов.**
- Чинишь: рваные переходы (переписать мостик), порядок «определение → пример → число», необъяснённые термины при первом употреблении, незавершённые мысли.
- НЕ правишь молча: глубокие структурные проблемы (статья тянет несколько тем, целый раздел не на месте, вывод не подготовлен всем текстом) — это вердикт пользователю, а не тихая переделка. Новые разделы не добавляй без спроса.
- Если связка ломается системно (материал на 2 статьи, скачки между темами) — **остановись и сообщи пользователю с диагнозом**, до языковой правки.

## Шаг 0.5 — Вердикт /methodology-gate + терминология клиента (ПЕРЕД языковой редактурой)

**Методология — зона /methodology-gate, не редактора.** Полная методологическая проверка (воронка, KPI, этапы проекта, роли, метрики) выполняется гейтом до редактуры. Здесь только:

1. Прочитай вердикт `/methodology-gate` из `pipeline.md` (строка «4b. Methodology gate»). Если гейт не пройден или не запускался для темы, где он обязателен (показатели / KPI / воронка / план продаж / аутрич / управление ОП) — **остановись и сообщи пользователю**: сначала /methodology-gate, потом редактура.
2. **Терминология клиента** — проверить по `<project>/data/company-context.md`. Для factor:
   - «успешные сделки», не «закрытые» (закрытыми бывают и проигранные)
   - «диагностика», не «аудит» как название КЭВ (аудит у ФП — платный трипвайер)
   - КЭВ — расшифровать при первом упоминании
   Однозначные термин→термин правки — исправить через replace-text до языковой редактуры.
3. **Претензии живого редактора клиента** — прочитать `<project>/data/review-patterns.md` и `<project>/data/ai-patterns-client-flagged.md`, если есть. Это золотая обратная связь: за что реально возвращают статью, и конкретные ИИ-паттерны, пойманные ревью (калибровка few-shot). Ревьюеры 1, 6 и 5 ДОПОЛНИТЕЛЬНО сверяют текст против этих файлов. Для crmgroup в файле: рефрен «честный X» (7 раз на статью, реакция клиента «иишно очень»), приставка «— гайд NNNN» в H1, тире в H1, структурные кальки «X: от А до Б» с тестом обратного перевода. ⚠️ Копий файла две и они не синхронны — читать ту, что относится к проекту. Для factor `ai-patterns-client-flagged.md` даёт три класса: A перечислимые обороты («дело не в X, а в Y», «X не равно Y»), B сквозные повторы (одна мысль в разных разделах, FAQ=пересказ тела), C открытые смэллы (сочетаемость «греют вхолостую», регистр «вешается», затянутый лид).

**Текущая дата** известна из контекста сессии; при сомнении — `date +%Y`. Если год в статье не совпадает с текущим — исправить в H1, SEO Title, cover_tag.

## Как работает /editor — фан-аут: Р0 (логика) → Р1–Р4 + Р6 → Р5 (основной режим)

Не один монолитный проход (так правила теряются — висящий глагол, повторы и т.п. проскакивают). Вместо этого — ревьюеры с узким фокусом. **Р0 «Логика и связка» — ГЕЙТ ПЕРВЫМ:** проверяет глобальный аргумент (сквозной тезис, переходы, define-before-use, обоснованность выводов, скоуп, таксономию). **Р1–Р4 + Р6** (ИИ-стиль, тон, структура, грамматика, сквозные повторы) — параллельно, *вычищают* язык. **Р5 «Живой язык»** — отдельный читательский проход, *добавляет* человеческую фактуру (ритм, голос), чтобы текст не был «правильным, но мёртвым».

**Шаг 1 — сначала Р0 «Логика и связка» (Agent). Если Р0 даёт вердикт «нужна структурная переработка» (статья тянет 2–3 темы, связка ломается системно) — ОСТАНОВИТЬСЯ, вынести диагноз пользователю ДО языковой правки** (нет смысла полировать язык в тексте, который надо перекроить). Мелкие правки Р0 (переходы, порядок «объясни→цифра») применить. **Затем — 5 ревьюеров Р1–Р4 + Р6 «Карта тезисов» (в ОДНОМ сообщении, параллельно). Р5 «Живой язык» — отдельным проходом ПОСЛЕ применения Р1–Р4/Р6 (см. ниже).** Каждому дать: полный текст статьи + проект/голос (из project.md) + ЕГО чеклист (ниже) + строку в промпт: **«примеры и детальные таблицы ✗→✓ — в `~/.claude/skills/editor/references/reviewer-details.md`, прочитай СВОЙ раздел»**. Каждый возвращает список находок в формате: `цитата → проблема → предлагаемая правка`. Только находки, не переписывать всю статью.

**Ревьюер 0 — Логика и связка (ПЕРВЫМ, до Р1–Р4; проверяет ГЛОБАЛЬНЫЙ аргумент, а не предложения).**
- **Сквозной тезис.** Есть ли у статьи ОДИН аргумент/дуга, который держит все разделы? Сформулируй его в одну фразу. Если не формулируется — статья расфокусирована (вердикт пользователю).
- **Связка на переходах.** Каждый H2 должен вытекать из предыдущего и вести к следующему. Ищи скачки «врывается без контекста», «внезапный блок», резкие смены темы. Мостик чинится переписыванием перехода («раз X дорожает — значит Y»), НЕ перестановкой разделов.
- **Define-before-use.** Термин (BANT, CPL, CAC, «предквалифицированный лид») и цифра НЕ должны появляться раньше, чем читатель к ним подведён. Порядок: определение/контекст → пример → число. Нарушения — пометить, поправить порядок.
- **Обоснованность выводов.** Вывод («поэтому нужен CRM») должен быть подготовлен предыдущим текстом. Если вывод «внезапен» — либо достроить подводку, либо пометить.
- **Скоуп.** Статья не тянет 2–3 темы разом? Если да — какой материал вынести/сжать. Это ВЕРДИКТ пользователю (не молчаливая правка).
- **Таксономия списков/таблиц.** В одном списке/столбце — сущности одного уровня (каналы ≠ инструменты ≠ источники). Смешение — пометить.
Формат: как у всех — `цитата → проблема → правка ИЛИ вердикт «нужна структурная переработка: …»`. Мелкие переходы/порядок Р0 правит; крупную структуру — выносит пользователю ДО применения Р1–Р5.

**Ревьюер 1 — ИИ и стиль.**
- Тире как приём (ритм/пауза/драма/«удар», вместо запятой/двоеточия/«и») — кандидат на замену; оставить только именное сказуемое без связки. Норма, замены и подсчёт — каноническое место: **Шаг 3**.
- ИИ-конструкции: эхо-объяснение, «X важно. Но…», антитеза «X, не Y», «Это не про X, а про Y», «С одной стороны… С другой стороны…» (нейтральный компромисс вместо позиции — запрещено), «на первый взгляд/казалось бы», «рассмотрим три момента», анафора ×3, эллипсис-удар («Это другое.»), самооправдание формата.
- **Формы-клише из ревью клиента (класс A в `ai-patterns-client-flagged.md`) — ловить обязательно:** «Чаще всего дело не в X, а в Y», «Это не просто X, это Y», «X не равно Y» (напр. «открыл письмо не равно готов купить»), заголовок-интрига «Дело не в X: где ломается Y», эхо-вывод-драматизация в конце абзаца («…именно в этом слепом пятне теряются деньги»). Читай `ai-patterns-client-flagged.md` и работай как «прокачанный читатель», который распознаёт нейросетевость: не только по списку, но и по общему запаху.
- **Сочетаемость и регистр (класс C):** странные связки «греют вхолостую», «упирается в потолок», «закрывать некому» → по-русски и конкретно; разговорщина в деловом тексте «ответственность вешается», «лид в мусор» → нейтрально.
- Штампы и вводные: «следует отметить», «важно понимать», «в современном мире», «в этом смысле», «интересно наблюдать»; усилители «очень/крайне/действительно»; абстрактные нейро-слова «сдвиг/поворот/переосмысление/манифест/жест».
- Антропоморфизм (даже мягкий: «пространство собирается»); кальки с английского и физические глаголы у абстрактных понятий; иностранные термины/бренды → русский; военные метафоры; драматическое слово в конце ради эффекта; ритм (не рубленый и не монотонный).

**Ревьюер 2 — Аудитория и тон.**
- Не сужать аудиторию: «нужно интернет-магазину» → «компаниям, которым нужно…» + примеры.
- Категоричность только обоснованная: «бессмысленно», «не потянет», «всегда/никогда» → «обычно», «не всегда корректно».
- Без снисходительности/разговорности: «поймите главное», «трём вещам», «всё просто».
- Заголовки экспертные, не бытовые; H1 отражает тип статьи; подзаголовки единым форматом.
- Вывод содержательный и компактный (не «выберется сам», не 3 абзаца об одном); не нагнетать, не «толкать в боль» резко.
- Предлог «про» (в значении «о») → «о/об/в отношении». Голос компании («мы»), без вымышленных личных историй. Внешние источники (Gartner, McKinsey…) расшифрованы при первом упоминании.

**Ревьюер 3 — Структура.**
- Дубли блоков: текст не пересказывает таблицу; FAQ не повторяет тело (для SEO — новые вопросы по ключам); один блок не повторяется между H2.
- Таблицы: ячейки конкретные, без оценок («зрелый», «недорого»); название столбца = содержанию; не мешать плюс/минус в одной ячейке; показывать лимиты/факты, не «возможности базовые»; названия (сервисов и т.п.) — отдельным столбцом; одна таблица на сущность.
- Единообразие подзаголовков и параллельных блоков (все вопросы ИЛИ все действия; одна глагольная форма в шагах).
- H2 — самостоятельный запрос, не «Что такое X»/«Заключение»; первый H2 не дублирует H1.
- **Шаблонная концовка = маркер автоматизма.** Заголовок последнего раздела НЕ должен быть дежурным «Что дальше»/«Выводы»/«Итого»/«Заключение»/«Подведём итог» — это узнаётся как ИИ-штамп (клиент прямо жаловался: «в каждой статье одинаково»). Финальный заголовок должен быть содержательным, из сути статьи (напр. вместо «Что дальше» → «Считать клиента и беречь базу»). Пометить, если концовка дежурная.
- Монотонная композиция: 3+ разделов подряд с одинаковой внутренней структурой (тезис → список → мини-вывод) — AI-паттерн, перестроить хотя бы один.
- Лид: прямой ответ или проблематика (TL;DR-формат — см. свой раздел в reviewer-details.md), не определение термина, не «в этой статье рассмотрим». Лишние абзацы/списки убрать. Кейс — с «грязной деталью», не только цифры.

**Ревьюер 4 — Язык и грамматика.**
- Висящий объект/глагол: у каждого глагола есть объект; в параллельных рядах все члены завершены. ✗ «как выбрать под задачи» → ✓ «какой выбрать под задачи».
- Повторы слов в соседних предложениях/заголовках → заменить/переписать.
- Опечатки, пропущенные глаголы, лишние запятые, согласование (падеж/род/число), порядок слов.
- Плеоназмы, канцелярит («имеет место»→«происходит»), номинализации→глаголы («осуществление рассылки»→«отправить рассылку»), сочетаемость («играть значение»→«иметь значение»), управление предлогов, деепричастные обороты, нанизывание родительных (3+ → переписать).
- Пассив → актив («была проведена работа» → «мы разобрали»). Расплывчатость → конкретика («лишнее», «несколько вещей» → что именно); точность дат/географии («с 2024 года» не устарело ли; «в рунете/в России» корректно ли).

**Ревьюер 6 — Карта тезисов (сквозные повторы; отдельный агент, метод — не «на глаз», а построением карты).**
Локально каждый абзац выглядит нормально — повтор одной мысли в разных разделах ловится ТОЛЬКО анализом всего текста. Обычный проход его пропускает (реальный промах: MQL/SQL определены дважды, «взять 30–50 заявок и послушать звонки» — трижды, «две половины воронки» — дословно в двух блоках подряд).
**Вход Р6 — вывод `shingles_check.py`:** оркестратор прогоняет скрипт ДО фан-аута (команда — в Шаге 3) и вкладывает его вывод (механические пары дублей между разделами и FAQ↔тело с Жаккаром) в промпт Р6. Карту строить ПОВЕРХ вывода скрипта, не вместо него: скрипт ловит текстуальные дубли, Р6 — смысловые перефразы. Метод:
1. Прочитай статью целиком и выпиши НУМЕРОВАННЫЙ список каждого отдельного тезиса / определения / примера / цифры и в каком разделе он появляется.
2. Отметь любой, что встречается **>1 раза**. Правило: каждый тезис/определение/пример — ровно один раз. Второе появление → вырезать ИЛИ развить новым содержанием (не перефразом).
3. **FAQ ↔ тело:** каждый ответ FAQ сверить с телом. Если пересказывает — пометить: заменить на вопрос, которого в теле нет, ответ добавляет новое.
4. **Стык абзацев:** конец абзаца не должен дублировать начало следующего (мысль перетекает мостиком, а не повторяется).
5. **Полотно:** раздел >150–200 слов без списка/подзаголовка/визуала — пометить на дробление.
Формат: `тезис → разделы, где повторяется (§N, §M) → что оставить, что вырезать/развить`. Это агент с широким контекстом (весь текст), запускать в общем фан-ауте с Р1–Р4.

**Ревьюер 5 — Живой язык (читательский проход, запускать ПОСЛЕ применения правок Р1–Р4 + Р6).**
Не вычищает плохое (это Р1), а проверяет, читается ли текст как написанный живым экспертом, а не сгенерированный. Прогон по почти-финальному тексту.
- Читка вслух: где спотыкаешься, где язык не поворачивается так сказать, где предложение приходится перечитывать.
- Ритм: чередование длины предложений. Всё одной длины (12–18 слов), каждый абзац с подлежащего, нет ни одного короткого (3–5 слов) — «мёртвый» ровный текст. Отметить, где нужен слом ритма.
- Голос и позиция: текст что-то утверждает или пресно пересказывает? Где нейтральный «обзор ради обзора» вместо живой экспертной речи. Есть ли «мы / из нашей практики».
- Картинка vs абстракция: «менеджер не выполняет план» (констатация) → «сливает каждого второго лида» (картинка). Где абстракцию можно заземлить в конкретный образ/цифру.
- Тест «сказал бы так живой эксперт коллеге?»: если фраза звучит как Википедия / методичка / пресс-релиз — отметить и предложить, как сказал бы человек. Сильные глаголы вместо «является/осуществляет/обеспечивает».
- Слабые места жизни: канцелярский ровный абзац, перечисление без интонации, вывод-резюме без энергии.
- ⚠️ НЕ добавлять взамен ИИ-приёмы (драма ради драмы, искусственный удар, антитеза) — это вернёт работу Р1. Живость ≠ пафос. Цель — естественная человеческая речь, не «ярче».
Возвращает: `цитата → почему звучит мёртво/гладко → как сказал бы живой человек`. Если текст и так живой — сказать прямо, не выдумывать правки.

**Шаг 2 — свод и применение.** Сначала свести Р1–Р4 + Р6 и применить (анти-ИИ / тон / структура / корректность / сквозные повторы: дедуп повторённых тезисов, чистка FAQ↔тело), ПОТОМ прогнать Р5 по обновлённому тексту и применить его находки. Дедуп по цитате. Конфликты (один смягчает, другой заостряет) решить в пользу ясности и голоса проекта; реальные неразрешимые — вынести пользователю. Конфликт Р1↔Р5 (Р1 убрал «удар», Р5 просит живее) — в пользу естественной речи: ни искусственного приёма, ни мёртвой гладкости; если живость требует приёма, переписать так, чтобы звучало как человек, а не ИИ-штамп. Применить к тексту (или к Google Doc через replace-text).

⚠️ Находки ревьюеров ссылаются на текст ДО правок. **Перед каждым replace проверь, что цитата ещё существует в документе** (после предыдущих правок текст мог измениться). Не нашлась — не пропускать молча: переформулируй правку по актуальному тексту.

**Шаг 3 — детерминированные гейты (механика скриптов и подсчётов).**

### 🔴 Тире — каноническое место правила (Р1, Gotchas и финальный чеклист ссылаются сюда)

**Уместно:**
- Именное сказуемое без глагола-связки: «Аудит — диагностика продаж»
- Список с опущенным глаголом: «Блок 1 — конверсия и выручка»
- Смысловой разрыв/неожиданность: «Позвонили — не взяли трубку»

**Не уместно (AI-паттерны с тире) и замены:**
- Вместо запятой перед «и»: «Нашли — и сразу исправили» → «Нашли и исправили»
- Переход между мыслями: «Менеджеры старались — результата не было» → «...старались, но результата не было»
- Антитеза «X — не Y»: «Начало — не конец», «Фотография — не система» → переписать развёрнуто
- Вместо двоеточия: «Вывод — нужно менять скрипты» → «Вывод: нужно менять скрипты» (в таблицах `<td>` — тоже двоеточие)
- Для «удара» в конце: «Корень проблемы — в другом» → «Корень проблемы в другом» (можно убрать совсем)

**HARD GATE — выполнить обязательно после всех правок.** Тире вредно везде — проза, таблицы, заголовки; считать суммарно. Лимит: **≤ 8 на статью, ≤ 2 в абзаце.** В text-режиме нет файла → Python `.count('—')`, не grep.

```python
total = text.count('—')
print(f"Тире всего: {total}")  # должно быть ≤ 8
for i, para in enumerate(text.split('\n\n')):
    c = para.count('—')
    if c > 2:
        print(f"Абзац {i}: {c} тире — НАРУШЕНИЕ: {para[:80]}")
```

Вывести результат: `Тире после правки: X (лимит ≤ 8) ✓/✗`. Если > 8 — убирать заменами выше до ≤ 8. Пропустить этот гейт нельзя.

## Шаг: Разметка визуализаций для /designer (handoff)

**После языковой правки** — пройди статью и отметь 2–3 места, где инфографика помогает читателю понять быстрее. Редактор видит смысл текста лучше, чем дизайнер, поэтому метки ставит он, а `/designer` идёт по ним, а не угадывает.

**Что хорошо ложится в визуализацию (типы = реальные шаблоны designer):**
- Перечисление признаков / условий / классов (без жёсткого порядка) → `cards-num`
- Пошаговый алгоритм / этапы / последовательные действия → `cards-badge`
- Воронка / последовательность с сужением → `funnel`
- 3–5 ключевых цифр / бенчмарков / цен, а также «было / стало», «проблема / результат» (2 карточки) → `stats`
- Плотная таблица, которую тяжело читать текстом → собрать из `cards-*` / `stats`

**Куда НЕ ставить:** в лид, FAQ, кейс, CTA, два раздела подряд.

**Формат метки** — вставить отдельной строкой в конце релевантного абзаца/раздела:

```
[ВИЗУАЛ: тип=cards-num | заголовок=Три класса сервисов рассылок | данные=Простой → С автоматизацией → Платформа данных; для каждого: что умеет + пример + цена]
```

Поля: `тип` (funnel / cards-num / cards-badge / stats) | `заголовок` | `данные`.

**`данные` = ГОТОВЫЙ ТЕКСТ для схемы, дословно из статьи, а не бриф «что показать».** Дизайнер ничего не сочиняет, он переносит твой текст один-в-один. Поэтому клади туда финальные подписи и цифры так, как они должны стоять на картинке (формулировки уже вычищены тобой от ИИ-шности). Пиши лейблы через разделители, без «покажи…», «нужно отразить…». Заголовок и подзаголовок тоже бери из текста раздела, не выдумывай слоганы.

Правила:
- 2–3 метки на статью, до 4 на лонгрид, не больше. Если мест нет — не выдумывать, поставить 0.
- Метка — это ТЗ, а не картинка. Дизайнер сам решит стиль по токенам клиента.
- Метки не считаются за тире и не идут в финальный текст для читателя (их снимет /designer или /publisher после генерации).

**Редактор ПРЕДЛАГАЕТ визуализации пользователю — не молчком.** В конце вывода вынеси отдельный блок «Предложение по визуалу» и для каждой схемы покажи: какой ВИД (тип + 1 строка почему этот вид подходит) и ГОТОВЫЙ ТЕКСТ к ней (дословно из статьи — заголовок, подписи, цифры, итог). Пользователь должен увидеть и утвердить ещё до /designer. Формат:

```
=== Предложение по визуалу (утвердить до /designer) ===
1. Вид: cards-num (3 карточки) — сравнить классы рядом нагляднее, чем текстом
   Заголовок: Три класса сервисов рассылок
   Текст: Простой (Unisender, Mailopost…; от ~600 ₽) | С автоматизацией (Sendsay…; от ~1 060 ₽) | Платформа данных (Mindbox…; от 9 990 ₽)
2. Вид: cards-badge (4 шага) — это пошаговый выбор, ложится в нумерованный поток
   Заголовок: Как выбрать сервис за 4 вопроса
   Текст: 1) Размер базы… 2) Частота… 3) Автоматизация… 4) Каналы → минимально достаточный класс
```

Тот же текст продублирован в инлайн-метках `[ВИЗУАЛ: …]` для /designer. Если пользователь поправит вид/текст — обнови метки перед передачей дальше.

## Gotchas

- **Не менять структуру и логику** — только язык и конкретность. Нельзя переставлять разделы, добавлять новые H2, убирать существующие.
- **Не переписывать кейс** — если кейс реальный (есть URL factor-prodazh.ru/case/), менять только язык. Если детали вызывают сомнение — пометить `[нужна деталь от клиента]`, не выдумывать.
- **Не убирать сленг продажников** — «дожимать», «сливать лида», «закрывать сделку» — это голос, а не ошибка.
- **Не «улучшать» тезисы** — если в тексте позиция «мы против X, потому что Y», не смягчать до «есть разные подходы».
- **Вымышленные личные истории убирать, не адаптировать** — «Клиент прислал мне…» → переписать на «В одном из проектов мы увидели…» или убрать.
- **Google Doc: replace-text только конкретными фразами** — не заменять куски длиннее 150 символов через replace-text, дробить на несколько замен.
- **replaceAllText иногда даёт 500** — известный баг Google Docs API. Fallback: найти индексы фразы через get-doc-structure, затем deleteContentRange (удалить диапазон) + insertText (вставить новый текст) по индексам. Не ретраить replace-text бесконечно.
- **Англицизмы в продажах — переводить всегда:** `churn rate` → «процент оттока», `SQL` (Sales Qualified Lead) → «квалифицированный лид», `Key Results` (OKR) → «ключевые результаты», `Accountability Chart` → «система подотчётностей», `funnel` → «воронка». Не оставлять даже если «понятно и так» — редактор видит аббревиатуры, пользователь блога нет. Таблица замен — reviewer-details.md, раздел Р1.
- **«Мы видели в нескольких проектах» — проверять:** если утверждение не верифицировано через реальные кейсы factor-prodazh.ru/case/ или company-context.md, убрать отсылку на «наш опыт» или переформулировать как принцип без ссылки на конкретные случаи. Придуманный факт от первого лица хуже безликого тезиса.
- **Тире — HARD GATE, не рекомендация** — правило целиком (стилистика, замены, подсчёт, лимиты) в одном месте: Шаг 3. Пропустить нельзя.

## Финальный вывод — по режиму

- **text-режим:** исправленный текст целиком в чат + перезаписанный `draft.md`, затем финальный чеклист, строка-флаг и SEO-блок.
- **doc-режим:** лонгрид в чат НЕ дублировать. Только: ссылка на Google Doc + финальный чеклист со статусами ✓/✗/⚠️ + строка-флаг + SEO-блок.

**Обязательная строка-флаг (в обоих режимах)** — её читает /methodology-gate, решая, нужен ли re-check 5b:

```
Методологическая фактура: не менялась
```
либо
```
Методологическая фактура: менялись разделы: <какие и что именно>
```

«Менялась» = правки затронули суть, а не формулировки: цифры/конверсии, воронку и её этапы, этапы проекта, KPI и метрики, роли, платность услуг. Косметика (стиль, ритм, тире, кальки) — «не менялась». При любом сомнении писать «менялись разделы: …» — гейт лучше прогонит лишний re-check, чем пропустит искажение.

Затем — уточнённый SEO-блок:

```
=== SEO-черновик (финализирует /seo-optimizer) ===
H1: ...
SEO Title (XX симв.): ...
SEO Description (XX симв.): ...
cover_subtitle: ...
cover_tag: ...
```
