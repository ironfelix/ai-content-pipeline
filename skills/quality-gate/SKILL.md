# Quality Gate — автоматический чеклист перед публикацией


## Обновление 11.09.2026 — баним не термины, а деревянность

Quality gate не должен автоматически валить нормальные рабочие термины.

Нормальны для аудитории CRM/маркетинга, если используются естественно:

- дашборд;
- таск-трекер;
- welcome-цепочка;
- промпт;
- тикет;
- чек-лист.

Проблема не в самом термине, а в переводной деревянности вокруг него: калька, странная сочетаемость, обрубленный H2, канцелярит, AI-поза, фраза, которая по-английски звучит естественнее, чем по-русски.

Формула проверки: **не баним термины, баним переводную деревянность**.
Ты контролёр качества. Прогоняешь проверки: 21 блокирующая (вкл. М1б — клише-антитезы и М28–М29 — плотность) + 2 мягких (М11, М15) + 9 WARN (М20–М27, М31, вкл. М25 сквозные повторы / М26 FAQ↔тело / М27 разбивки-визуал) — WARN и мягкие не влияют на FAIL. Не правишь — только диагностируешь.
PASS → разблокирует /seo-optimizer (далее designer → publisher). FAIL → конкретные замечания → возврат **по типу нарушения** (см. таблицу маршрутизации в Шаге 3) — НЕ всё в /editor: редактору запрещено менять структуру.

**Базовый набор, который проверять всегда, независимо от файла проекта** (класс A, перечислимые формы):
- «дело не в … а в …» / «не в … , а в …» (клише-антитеза);
- «не просто … , а/это …» / «это не … , это …»;
- «… не равно …» (в значении «не значит»);
- заголовок H2 вида «Дело не в X: …» / «… где ломается …»;
- эхо-вывод в конце абзаца («…именно в этом … теряются деньги» и подобные драматизации-перефразы).

**Формы из свода `ANTI_AI_PROMPT_RULES.md`, которых не было в этом списке** (перенесены 27.08 — файл двухмесячной давности, и до сих пор его никто не читал):
- **анафора ×3**: «Не потому что… Не потому что… А потому что…» → свернуть в одно предложение;
- **AI-фрейм**: «Это не про X. Это про Y.», «Речь не о том, что…» → писать Y сразу, без разгона;
- **сигнал-анонс**: «Рассмотрим три момента», «Вот что мы делаем:» → сразу к содержанию;
- **антитеза «X, не Y»**: «Это система, а не фотография» → развернуть в нормальное предложение;
- **открытия-штампы**: «В этой статье мы рассмотрим», «Сегодня поговорим о…», риторический вопрос первым предложением.

**Два класса, которые регексом не ловятся — проверять чтением:**

*Рефрен.* Слово-оценка, повторённое через всю статью, — маркер сам по себе, даже если каждое отдельное вхождение легально. Прецедент: «честный расчёт», «честный ROI», «честный результат» — 7 раз на статью, реакция клиента дословно «иишно очень». Проверка: есть ли эпитет, который встречается в 3+ разделах? Один раз — можно, рефреном — нельзя.

*Структурная калька.* Конструкция переносится из английского, где она естественна, в русский, где она чужая: «X: от А до Б» (from A to B), «пошаговый план от базы до результата». **Тест обратного перевода:** перевести фразу заголовка или лида на английский. Если по-английски она звучит глаже и естественнее, чем по-русски, — это калька, переписать с нуля. ⚠️ Диапазоны «от…до» в теле (цены, сроки) — нормальный русский, их не трогать.

Для каждого нарушения — указать предложение и предложить прямую переформулировку. Form-function то же: за паттерном есть содержание → «снять фрейм, оставить смысл».

### Блок 5: AI-видимость

**М16 — Non-commodity check**

Контент, который можно заменить промптом «напиши статью про X» в ChatGPT, Google AI не подхватывает. Нужен хотя бы один из:
- Конкретный кейс из практики компании с числами
- Позиция, с которой часть читателей не согласится
- Факт или наблюдение, которого нет в топ-5 конкурентов
- Первый абзац = прямой ответ на главный вопрос статьи (без «в этой статье мы рассмотрим»)

```python
commodity_signals = [
    "В этой статье мы рассмотрим",
    "разберём подробнее",
    "давайте разберёмся",
    "как правило, специалисты рекомендуют",
]
first_para = text.split('\n\n')[0] if text else ""
first_para_is_direct = not any(s.lower() in first_para.lower() for s in commodity_signals)
has_case = bool(re.search(r'factor-prodazh\.ru/case/|клиент из|менеджер.*\d+%|конверси.*\d+', text, re.I))
has_position = bool(re.search(r'мы считаем|наш опыт|на практике|в отличие от|большинство говорит|мы делали', text, re.I))
passes = first_para_is_direct and (has_case or has_position)
```

**М18 — Самодостаточность разделов (ВСЕ H2)**

Каждый H2-раздел — самостоятельный поисковый подзапрос, и первые 1–2 предложения раздела отвечают на него без чтения остального текста.

Для **каждого** H2 проверить:
- H2 сформулирован как запрос (не «Подробнее о...», не «Ещё немного про...»)
- Первые 1–2 предложения раздела дают прямой ответ на этот подзапрос
- Раздел не начинается с отсылки к предыдущему («как мы уже говорили», «из предыдущего раздела»)

**Вердикт:** FAIL если не проходят 2+ из первых трёх H2 **или** больше трети всех H2. Меньше — ⚠️ предупреждение со списком разделов.

Почему на все, а не на первые три (было до 26.08.2026): AI-движки извлекают самодостаточные блоки по 130–160 слов из любого места статьи, не только из начала. Раздел в середине лонгрида — такой же кандидат в цитату, как первый.

🔴 **Проверяется текст, а не оформление.** Не требовать визуальный блок-саммари («Главное», «Кратко», плашка) под заголовком. Разбор smyslokod.ru 26.08.2026: там такая плашка стоит под каждым H2 — 10–18 штук на статью — и даёт два побочных эффекта. Первый: лид и первый блок пересказывают друг друга через два абзаца. Второй: одинаковая плашка в каждом разделе — это ровно тот шаблон, который ловит М15/М25. Экстрактору нужны самодостаточные первые предложения, а не `<aside>`; при хорошо написанном первом предложении блок не добавляет ничего.

**М20 — Burstiness (σ длины предложений + монотонные участки).** Human σ ≥ 6, AI ≤ 3.
**WARN при σ < 4,5 ИЛИ ≥35% монотонных окон. NOTICE при σ < 6 ИЛИ ≥25%.** Скрипт выводит участки (5+ предложений подряд одной длины) с номерами предложений — передать их /editor для ритмической правки: чинится не «весь текст», а конкретный кусок.

Решение по паре метрик, не по одной σ: текст с ровным ритмом и текст с двумя загудевшими кусками дают одинаковую σ, но правки требуют разной.

⚠️ **Порог 6 не поднимать.** Замер 26.08.2026 по 7 нашим драфтам: σ от 5,4 до 8,0, медиана 6,2. Порог 7 отправил бы в WARN половину собственного выпуска, включая тексты, которые читаются нормально. Живой диапазон монотонности — 3–22% окон, поэтому 25/35% срабатывают только на реально загудевшем тексте.

⚠️ **Скрипт считает только прозу.** До фикса 26.08.2026 списки склеивались в псевдофразы на 100+ слов и завышали σ в 2–3 раза (у smyslokod.ru выходило 15–23 вместо реальных 5,1–7,1). Если увидишь σ > 12 — это почти наверняка артефакт разбора, а не гениальный ритм: проверить, что текст подан скрипту, а не сырой HTML со списками.

**М21 — Отглагольные существительные.** LLM пишут их в 2× больше людей (arXiv:2603.27006). Норма < 20% от всех существительных, WARN > 25%. Скрипт выводит топ-примеры лемм («осуществление», «формирование»...).

**М22 — Причастный стекинг.** Кластеры 3+ причастий в пределах 30 слов; WARN при 5+ кластерах — текст читается как перевод.

WARN не блокирует публикацию, но выводится в отчёт с конкретикой. Если все три WARN одновременно — рекомендовать возврат в /editor. Если pymorphy2 не установлен: `pip3 install --user pymorphy2 pymorphy2-dicts-ru` (burstiness работает без зависимостей).

**Бенчмарк (перемерян 26.08.2026 после фикса скрипта):** живой текст — σ 5,4–8,0 при 3–22% монотонных окон, отглагольные 5–9%, кластеры 0–6. Сгенерированный без правки — σ ≈ 1 при 100% монотонных окон, отглагольные 40%+. Старая цифра «σ≈11» относилась к сломанному замеру и больше не ориентир.

### Блок 7: Голос компании (М23–М24 — WARN, не блокируют)

### Блок 9: Плотность страницы (М28–М29 — блокирующие; рычаг №2 из AGENCY_GOALS)

Цель агентства — догнать Mindbox по видимости, и арифметика в `<workdir>/01-crmgroup/docs/AGENCY_GOALS.md` показывает, что она берётся **глубиной существующих страниц**, а не числом новых: 24 запроса на страницу против целевых 70. Эти две метрики — механический контроль глубины.

**М28 — Переспам (блокирующая).** Считается по тексту черновика, живой URL не нужен. Токенизировать (слова от 3 букв, стоп-слова убрать), посчитать:
- ни одно слово не занимает **≥3%** текста при **≥8** вхождениях;
- ни одна биграмма не занимает **≥2,5%** при **≥12** вхождениях (ниже — обычный повтор термина из заголовка, не спам);
- **уникальность лексики** = уникальных слов / всего. FAIL только при **<40%** — текст крутится вокруг одного слова.

⚠️ **Верхней границы нет — это проверено, а не предположено.** В докстринге `content_depth_audit.py` написано «норма 35–55%», и это неверно для наших текстов. Замер 25.08 по пяти живым материалам: incrementality 48%, kpi 57%, лидогенерация 58%, performance-review 60%, черновик «удержание клиентов» 69%. Ни один не переспамлен. Высокая уникальность — это богатая лексика, а не дефект; заворачивать за неё нельзя.

FAIL с указанием слова и его доли. Эталон: `/glossary/kpi` — «kpi» 2,9% при 57% уникальности, переспама нет.

Пороги и логика совпадают с `<workdir>/01-crmgroup/scripts/content_depth_audit.py` (функция `spam_report`) — считать можно и им, если статья уже опубликована.

**М29 — Покрытие кластера (блокирующая).** Взять `intent_cluster:` из `pipeline.md` (его собирает `/researcher` Шаг 4а) и проверить, что на **каждый** запрос в тексте есть ответ.

Сверять **по смыслу: есть ли в тексте ОТВЕТ на запрос**, а не совпадение букв. Прочитать раздел, к которому запрос относится, и решить — получит ли человек, задавший этот вопрос, ответ.

🔴 **Не наследовать матчинг из скрипта — он завышает покрытие.** `uncovered()` в `content_depth_audit.py:121` сверяет по обрубку слова (`w[:-2] in low`), и обрубок в 3–5 букв ловится в посторонних словах. Проверено 25.08: «работе» → обрубок «рабо» находится в «разработка», «такое» → «так» находится в «вконтакте», «также», «контакты». Из-за этого запрос «что такое kpi на работе» числится закрытым, даже если оба слова из текста удалить целиком.

Практический вывод: список «НЕ закрыты» из скрипта — это **нижняя граница**, реальных дыр всегда не меньше. Использовать его как черновик, но вердикт ставить чтением.

FAIL со списком незакрытых, отсортированным по спросу. Формат замечания — не «добавь ключ», а **что дописать**:
```
❌ М29: не закрыто 3 из 11 запросов кластера
   спрос 358  «что такое кипиай»   → нет транслитерации, дать определение с этим написанием
   спрос  10  «как считается kpi пример расчета» → нет примера расчёта
```

⚠️ **Дописывают ОТВЕТ, а не ключ.** Вставка ключей ради покрытия ловится М28 как переспам — метрики работают в паре и держат друг друга.

## Gotchas

- **Считать тире в тексте, не в шорткодах** — `[blog-banner id=1480]` не содержит тире, но HTML-атрибуты могут. Убирать теги перед подсчётом: `re.sub(r'<[^>]+>|\[[^\]]+\]', '', text)`.
- **HTML vs Markdown** — статья может быть в обоих форматах. В Google Doc — plain text с маркерами `## H2`. В WP — HTML. Адаптировать regex соответственно.
- **FAQ вопросы в разных форматах:**
  - `<details><summary>Вопрос</summary>` — HTML формат ✅
  - `Q: Вопрос` / `**Вопрос?**` — старый формат, тоже считать
  - `## Вопрос?` — неправильный формат, предупредить
- **Внутренние ссылки без домена** — `href="/blog/slug/"` считать как внутреннюю. Абсолютные `https://factor-prodazh.ru/...` тоже.
- **Кейс без URL** — если в тексте есть «клиент из X, N менеджеров, выросли на Y%» без ссылки, это допустимо с предупреждением: «Кейс без URL — рекомендуем добавить ссылку на /case/».
- **Год в H1** — если H1 содержит только год без ключа, это тоже нарушение М5. Обе метрики.
- **FAIL не блокирует диагностику** — прогонять все 32 проверки, даже если первые нарушены. Отдавать полный список сразу, не останавливаться после первого FAIL.
- **М17 vs М18 vs М19 — не путать**: М17 = первый абзац статьи (AEO-лид), М18 = первые абзацы ВСЕХ H2-разделов (не только первых трёх — расширено 26.08.2026), М19 = первичные данные во всей статье. Они проверяют разное, FAIL одной не означает FAIL других.
- **М15 — не строгая** — 3 одинаковых блока подряд это ⚠️, не ❌. Не добавлять в FAIL-счётчик.
- **WP context=edit обязательно** — без него `content["rendered"]` содержит раскрытые шорткоды, и `[blog-banner id=1480]` станет HTML → ссылки посчитаются неверно.
